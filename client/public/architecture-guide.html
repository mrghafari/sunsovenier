Layer 3: Storage Layer (Data Access)

الگوی Repository Pattern

هر فایل *-storage.ts یک Repository است که تمام عملیات دیتابیس یک domain را مدیریت می‌کند.

// مثال: customer-storage.ts class CustomerStorage { // CRUD Operations async createCustomer(data: InsertCustomer): Promise<Customer> async getCustomerById(id: number): Promise<Customer | undefined> async updateCustomer(id: number, data: Partial<Customer>) async deleteCustomer(id: number): Promise<void> // Business queries async getCustomerOrders(customerId: number): Promise<Order[]> async getCustomerWallet(customerId: number): Promise<Wallet> }

مزایای الگوی Repository:

  • ✅ Separation of Concerns: منطق دیتابیس از routes جدا است
  • ✅ Reusability: قابل استفاده در چند route
  • ✅ Testability: راحت‌تر قابل تست
  • ✅ Type Safety: TypeScript types برای همه عملیات

🔐 معماری Authentication & Authorization

Session-Based Authentication:

// Express Session + PostgreSQL Store app.use(session({ store: new (connectPg(session))({ pool: db, tableName: 'user_sessions' }), secret: process.env.SESSION_SECRET, resave: false, saveUninitialized: false, cookie: { secure: false, // true در production httpOnly: true, maxAge: 24 * 60 * 60 * 1000 // 24 hours } }));

Multi-Role Authentication:

نوع کاربر Login Endpoint Session Key
مشتری /api/customers/login req.session.customerId
ادمین /api/admin/login req.session.adminId
فروشنده /api/vendors/login req.session.vendorId
⚠️ نکته امنیتی مهم:

در سیستم Multi-Vendor، همیشه باید با vendorId فیلتر کنید تا Cross-Vendor Data Leakage رخ ندهد!

🛒 معماری E-Commerce Workflow

Order Processing Pipeline:

1. Customer Cart ↓ 2. Checkout ↓ 3. Payment (Bank Gateway / Wallet / Bank Transfer) ↓ 4. Order Created ↓ 5. Order Management Workflow: ├─ Financial Review (تایید مالی) │ ↓ ├─ Warehouse Processing (پردازش انبار) │ ↓ └─ Logistics Delivery (تحویل) ↓ 6. Order Completed

Order Management States:

  • Payment: pending_payment, payment_uploaded
  • Financial: financial_reviewing, financial_approved
  • Warehouse: warehouse_pending, warehouse_approved
  • Logistics: logistics_dispatched, logistics_delivered
  • Final: completed, cancelled

🏪 معماری Multi-Vendor Marketplace

الگوی Vendor Isolation:

🔒 امنیت = اولویت اول!

همیشه از INNER JOIN با vendorId استفاده کنید تا فقط داده‌های مربوط به آن vendor نمایش داده شود.

// ✅ SECURE: INNER JOIN با vendorId const vendorProducts = await db .select() .from(shopProducts) .innerJoin(vendors, and( eq(shopProducts.vendorId, vendors.id), eq(vendors.id, req.session.vendorId) )); // ❌ INSECURE: بدون فیلتر vendorId const allProducts = await db .select() .from(shopProducts); // همه محصولات!
